Loop Engineering：给 Agent 设计循环的工程学

一次任务是一个循环，一个项目是一个循环，Agent 的自我改造还是一个循环。区别不在循环本身，而在状态的生存期，以及状态载体的抽象层级。

用过 Claude Code 这类 coding agent 的人对 agent loop 都不陌生：模型读上下文，调用工具，观察结果，决定下一步，直到任务完成或预算耗尽。这个感知—行动—观察的循环在三个时间尺度上同时运转：一次会话内的任务执行、横跨数周的项目演进、Agent 对自身能力的改造。Claude Code loop design primer 把这组设计问题归入 loop engineering 的实践范畴。本文以它提出的三层框架为骨架梳理相关文献：Task Loop（把一次任务做对）、Project Loop（把项目做下去）、Meta Loop（让 Agent 改造自己）。

这个框架在理论上有现成的对应物。1999 年 Sutton 等人的 Options Framework [15] 把"跨多步的抽象动作"（option）形式化为策略加终止条件，不同时间尺度的决策可以嵌套组合。套到今天的 Agent 上：Task Loop 是执行一个 option，Project Loop 是 option 之间的状态继承，Meta Loop 是学会创建新的 option。

一、Task Loop：把一次任务做对

Task Loop 处理单次任务内的执行闭环。起点是 ReAct [1]：模型交替输出推理（Thought）和动作（Action），观察结果写回上下文。今天几乎所有 agent 框架的骨架都是这个结构。

随后两个工作在循环里加入反馈。Self-Refine [2] 让同一个模型生成、自评、修订，迭代到满足停止条件；Reflexion [3] 在多次尝试之间引入语言化的经验记忆：失败后生成一段自我反思，存入 episodic memory，作为下次尝试的上下文。等效于用自然语言做策略更新——不微调参数，只积累复盘记录。

工程化转折点是 SWE-agent [6]。它追问的不是循环结构，而是动作空间：Agent-Computer Interface（ACI）的设计质量直接决定循环成败，暴露给 Agent 的每个命令必须有明确的反馈信号，否则模型会在低效路径上反复空转。SWE-agent 在 SWE-bench [4]（2,294 个真实 GitHub issue）上创下当时的最好成绩。CodeAct [5] 从另一侧收敛到同一结论：动作空间统一为可执行的 Python 代码，比 JSON 之类的结构化格式更高效——代码是表达复杂动作最紧凑的接口，且执行本身就是验证。

反例来自 Huang 等人 [16]：没有外部反馈时，让 LLM 自查自纠通常无效，甚至降低原本正确的输出质量。这条结论划出了 [2][3] 的适用边界——自我反馈循环有效的条件，是反馈信号锚定在真实环境上：单元测试、任务成功判定、对具体失败轨迹的分析。模型对自己输出的判断不算。

Task Loop 的设计要点：动作空间紧凑且可执行；每次循环接回真实环境信号；反思针对具体失败，不做泛泛自评。

二、Project Loop：把项目做下去

Task Loop 的状态随上下文结束而消失。Project Loop 的状态必须活在上下文之外：文件、数据库、记忆系统。

正向机制看 Voyager [7]。它在 Minecraft 里靠三个部件做开放式探索：自动课程生成器提出难度递增的任务；迭代式提示机制根据环境反馈修正代码；Skill Library 把每个验证通过的技能以代码形式存入向量库，供后续检索和组合。获得新物品的速度是此前方法的 3.3 倍，且技能库跨世界可用。这一轮循环的产出成为下一轮循环的输入，能力以资产形式累积。

负向证据来自两篇 2026 年的基准研究。SlopCodeBench [8] 测量 coding agent 在长期迭代中的退化：agent 反复扩展自己写的代码，36 个问题、196 个 checkpoint，最好的 agent 只通过 14.8%；77% 的轨迹出现结构侵蚀（复杂度堆积到少数函数），75.5% 出现冗余膨胀。对照 473 个开源仓库的 git 历史，agent 代码冗余是 2.3 倍，侵蚀程度是 2.0 倍。一个关键细节：显式的质量约束能把初始冗余和侵蚀降低三分之一，但退化速率不变——指引改变起点，改变不了斜率。

SWE-Chain [9] 把链式程度再推进一步：跨版本的包升级，每次升级都建立在 agent 上一次交付的代码库上，9 个真实 Python 包、155 个版本迁移串成 12 条升级链。考验的是状态继承：上一版遗留的代码，全部是这一版的初始条件。

系统层面，Agent Memory [10] 对十个代表性记忆系统做了首个系统级刻画：提出四轴分类法，用分阶段剖析工具把成本归因到构建、检索、生成三个环节。核心结论是记忆系统的设计选择会系统性地在写路径（构建与更新）和读路径（检索）之间搬移成本。记忆架构是有真实成本曲线的系统设计问题，不是加一个向量库就完事。

Project Loop 的设计要点：状态资产化（skill library 是正面教材）；为退化设置监控与治理（SlopCodeBench 的证据表明退化是常态而非例外）；按读写成本曲线选型记忆架构。

三、Meta Loop：让 Agent 改造自己

Meta Loop 的特征是优化对象逐级上移，四级台阶：

第一级优化 prompt。DSPy [11] 的做法是"编程而非提示"（programming, not prompting）：声明式模块组成 pipeline，optimizer 自动搜索每个模块的提示词。开发者只写控制流，提示词是可学习参数。第二级优化 prompt 的搜索方式。GEPA [12] 不做盲目搜索，而是从执行轨迹提取反思文本，用遗传搜索加 Pareto 前沿选择进化提示词：平均比强化学习方法高约 10%，rollout 预算最多省 35 倍。和 Reflexion 一样，从轨迹学习再次胜过从标量奖励学习。

第三级优化工作流。EvoAgentX [13] 把 DSPy、TextGrad、AFlow 等优化算法收进统一框架，对多 agent 工作流的提示词、工具配置、执行拓扑做自动进化。第四级优化 agent 自身的代码。Darwin Gödel Machine [14] 修改驱动自己的代码库——工具、工作流、搜索策略——以 SWE-bench 得分为选择压力，维护自我修改版本的档案库做开放式探索。SWE-bench 得分从 20% 提到 50%，改进出的组件（如更反思性的工具调用）可迁移到其他任务。

四级台阶推的是同一个边界：什么可以被循环改变。从参数（提示词）到结构（工作流）再到 agent 的自我定义（代码）。每外推一层，验证闭环都更贵、更慢，且更依赖基准的代表性。DGM 的选择压力是 SWE-bench，而 SWE-bench 能否代表真实工程能力，正是 SlopCodeBench 这类研究提出质疑的地方。

DeepSeek Super-agent 把 Watchdog 放在主系统之外，由它定期检查 Worker 的实际进展，并在任务停滞或偏离目标时介入。维护者也可以通过 Watchdog 在线调整提示词和触发规则，让后续任务按更新后的策略执行。[18]

要把这种调整接成一个有人参与的 Meta Loop，可以在普通讨论频繁误触发 Worker 时收紧规则，再用一批新事件检验误触发是否减少、有效请求是否仍得到处理。对照验证是本文基于原文所述能力提出的设计。

四、跨层的设计原则与开放问题

三层放在一起，有四条贯穿的设计原则：

  1. 状态的生存期决定架构。 Task Loop 的状态随上下文蒸发，关键是信号如何接回；Project Loop 的状态跨会话存活，关键是资产化与记忆架构；Meta Loop 的状态写进 agent 自身，关键是版本管理与回滚。
  2. 验证闭环决定循环成败。 从 [16] 的教训到 [14] 的成功，有效的自我改进循环都锚定外部验证信号：单元测试、基准得分、环境反馈。没有验证闭环的反思是噪声源。
  3. 退化是长期循环的默认结局。 [8] 表明即使功能验证通过，代码质量仍在持续恶化。质量度量必须进循环，单靠"测试通过"一道闸门挡不住。
  4. 层级上移，工程重心从提示词转向系统。 Task Loop 的部分问题可以靠 prompt 工程解决；Project Loop 和 Meta Loop 的问题是存储、检索、调度、版本控制。

开放问题：自我纠错在什么条件下可靠（[16] 与 [2][3] 的边界尚未厘清）；长期循环的质量治理是否存在持续有效的干预手段（[8] 显示指引改变不了退化速率）；Meta Loop 的选择压力如何避免过拟合基准（Goodhart 效应的 agent 版）。
